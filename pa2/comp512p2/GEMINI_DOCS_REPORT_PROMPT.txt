2. SYSTEM ARCHITECTURE & PROTOCOL DESIGN:
   • Explain the Replicated State Machine (RSM) model: each player maintains a local island replica; moves (L, R, U, D) must execute in identical Total Order.
   • Update-Anywhere model: each node acts as a unified Proposer, Acceptor, and Learner for moves generated by its local player (no primary redelegation).
   • Instance & Ballot Abstraction: The game progresses as a sequence of Paxos instances (turns k = 1, 2, 3...). Each instance agrees on one move value. Monotonic Ballot IDs are tuples: BallotID = (ballotSequenceNumber, processIdentifier) with lexicographical tie-breaking.
   • Three-Phase Consensus over GCL:
     - Phase 1 (Prepare/Promise): Proposer broadcasts PROPOSE(k, ballotID). Acceptors update maxBallot[k] and reply with PROMISE containing highest previously accepted ballot/value.
     - Phase 2 (Accept/Ack): Upon majority promises (floor(N/2) + 1), proposer selects value (adopting highest promised accepted value or its own) and broadcasts ACCEPT?(k, ballotID, value). Acceptors accept if ballotID >= maxBallot[k] and reply ACCEPT_ACK.
     - Phase 3 (Commit/Confirm): Upon majority acceptance, proposer commits value and broadcasts CONFIRM(k, value) to all nodes.
   • In-Order Buffer: Acceptors/Learners buffer out-of-order committed turns and release them sequentially to the application thread via acceptTOMsg().
