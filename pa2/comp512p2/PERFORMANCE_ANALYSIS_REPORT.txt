we empirically evaluated our Paxos total order layer across player counts N ∈ {2, 3, 5}
and move intervals I ∈ {100, 50, 20, 10, 5, 0} ms. Each run executed 50 moves per player
with a deterministic pseudo-random seed (randseed = 123456789) on McGill SOCS Unix nodes.

total order event sequences and end-state map grids across all replicas.

2. QUESTION A: IMPACT OF MOVE INTERVAL AND GROUP SIZE ON LATENCY & THROUGHPUT

Observations (Figures 1 & 2):
Across all group sizes N, decreasing the move interval from 100 ms down to 10 ms triggers
steep throughput gains: 1.58× for N=2 (8.59 to 13.56 moves/s), 1.57× for N=3 (12.75 to
19.97 moves/s), and 1.41× for N=5 (20.95 to 29.45 moves/s). Average move latency drops
proportionately: from 116.38 ms down to 73.77 ms (N=2), 78.46 ms to 50.08 ms (N=3), and
47.74 ms to 33.95 ms (N=5). Below 10 ms, throughput gains taper into an asymptotic
saturation plateau. Larger groups consistently achieve higher aggregate throughput:
at 100 ms, N=5 delivers 20.95 moves/s versus 8.59 moves/s for N=2 (2.44× higher); at 0 ms,
N=5 peaks at 33.16 moves/s compared to 14.89 moves/s for N=2 (2.23× higher).

Discussion & Analysis:
The system transitions between two distinct operational regimes:
1. Sleep-Bound Regime (I ≥ 50 ms): Single-turn Paxos consensus requires ~3–5 ms.
Because the inter-move pause is substantially larger than consensus latency, the consensus
engine remains idle >90% of the execution time. Parallel players submit moves in largely
disjoint time windows with minimal Phase 1 ballot clashes. Group throughput scales linearly
with process count N because concurrent players pipeline proposals across distinct turns.
2. Consensus-Bound Regime (I ≤ 5 ms): When the move interval vanishes, players submit
proposals continuously. Threads contend concurrently for the same uncommitted turn in
Phase 1, triggering ballot preemptions. Larger groups require larger majority quorums
(⌊N/2⌋ + 1, increasing from 2 to 3) and generate O(N²) TCP messages across the GCL mesh,
inflating socket queue latency and causing throughput growth to plateau asymptotically.

3. QUESTION B: PROCESS FAIRNESS UNDER HIGH CONTENTION

Observations (Figure 3):
At I = 100 ms, turn allocation is balanced across all players (50 moves each, exactly 50.0%
for N=2, 33.3% for N=3, and 20.0% for N=5). Under zero-interval saturation (I = 0 ms), all
players still eventually commit all 50 moves due to our robust "No-Drop" retry policy.
However, early turn allocation exhibits a distinct temporal bias: lower-numbered player IDs
(Player A, followed by Player B) capture a disproportionate share of the earliest turns
in the total order sequence, while higher-numbered players (e.g. Player E) experience
frequent Phase 1 ballot preemption and must retry in later turns.

Discussion & Analysis:
This systematic scheduling priority originates from three architectural factors:
1. Deterministic Ballot Tie-Breaking: Monotonic ballot IDs are assigned as
BallotID = (ballotSeq × 100 + processId). When competing proposers concurrently initiate
Phase 1 with identical sequence numbers, acceptors deterministically promise the proposal
with the higher numerical tie-breaker and issue DENY messages to lower-priority nodes.
2. Local Loopback Zero-Delay Advantage: In our co-located multi-process deployment, each
node runs a Proposer, Acceptor, and Learner. Local proposals update the local acceptor
instantaneously in memory/loopback, whereas remote Phase 1 packets incur operating system
socket transit latency. A proposer reliably captures its own local promise first.
3. Sequential GCL Socket Servicing: The GCL transport layer services incoming TCP socket
connections sequentially based on port binding order, consistently giving priority to
early-bound descriptors belonging to lower player IDs.

4. QUESTION C: MAXIMUM THROUGHPUT SATURATION & CEILING

Observations (Figure 1):
System throughput does not scale indefinitely as the move interval approaches 0 ms.
Performance curves flatten noticeably between I = 10 ms and I = 5 ms, reaching maximum
saturation at 0 ms. For N=2, reducing interval from 5 ms to 0 ms yields only a 5.4% gain
(14.13 to 14.89 moves/s). For N=3, the gain is 7.8% (20.45 to 22.05 moves/s), and for N=5,
the gain is 8.8% (30.47 to 33.16 moves/s). Maximum system throughput caps at 33.16 moves/s.

Discussion & Analysis:
The saturation ceiling is established by the physical consensus latency floor (~30 ms per turn
under contention), comprising two sequential network round trips (Phase 1 Propose/Promise +
Phase 2 Accept/Accepted) plus GCL TCP serialization and Phase 3 Commit broadcast. When the
move interval drops below this physical floor, the idle sleep gap completely disappears and
threads block inside broadcastTOMsg awaiting majority acknowledgments. Decreasing interval to
0 ms merely inflates internal socket buffers without accelerating consensus round completion.
Furthermore, each broadcast requires (N-1) TCP transmissions, generating up to 44 network
packets per turn for N=5. Socket buffer lock contention, OS context switching, and cascading
retry storms absorb available CPU cycles, bounding the maximum achievable consensus rate.

5. CONCLUSION

Paxos achieves near-linear throughput scaling and equal fairness under moderate workloads
(I ≥ 50 ms). Under intense contention (I → 0 ms), system throughput saturates against a
physical round-trip latency floor, network overhead scales quadratically with group size,
and deterministic ballot tie-breaking introduces temporal ordering bias.
